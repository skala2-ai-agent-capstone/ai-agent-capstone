# Agent 자료 수집 성능 개선 — 2026-10-25

분석 기준은 `skala2-ai-agent-capstone/ai-agent-capstone`의 `79abfc1`이다.
백엔드가 정지된 상황에서 재현할 수 있는 최종 평가 자료 수집 지연을 개선했다.
외부 API·MCP 도구 이름, 요청 인자, 응답 스키마, RabbitMQ 계약, 저장 순서는 변경하지 않았다.
MCP 서버 코드, 모델, 프롬프트, 승인 기준, 채점·근거 검증 규칙도 그대로다.

## 분석과 선택

| 영역 | 확인한 실행 구조 | 이번 판단 |
| --- | --- | --- |
| 기준 생성 | 선택된 업무 유형 → 내규 조회 → 생성·검증 → 승인 | 독립적으로 병렬화할 조회가 적고 생성 품질 검증이 필요하므로 유지 |
| 중간 피드백 | 실행 범위 확인 → 최근 대화 조회 → 모델 생성·검증 → 저장 | 앞 단계 결과에 의존하는 흐름이므로 유지 |
| 개인 최종 평가 | 실행 범위·업무 확인 → 여러 산출물·기록·참조 조회 → 모델 평가·검증 → 저장 | 독립 읽기가 순차 실행되어 우선 개선 |
| 팀 평가 | 서버 집계 스냅샷 → 모델 선택·검증 → 저장 | 서버 집계와 모델 측정 없이 변경할 근거가 부족하여 유지 |

최종 평가의 동일한 수집 함수는 저장된 기준을 사용하는 Worker와 승인형 평가 양쪽에서 쓰인다.
프롬프트 입력에는 원문과 근거 카탈로그가 함께 들어가므로 토큰 절감 후보가 있지만,
실제 모델의 평가 품질을 측정하지 않은 상태에서 근거를 줄이지 않았다.
전체 응답 시간에서 LLM이 차지하는 비중은 이번 실험으로 알 수 없다.

## 구현

- `integrations/parallel_reads.py`: 독립 읽기를 최대 4개 작업으로 처리하고 입력 순서대로 반환한다.
  오류나 상위 취소 시 남은 작업을 취소하고 종료를 기다린다. 원래 예외와 재시도 속성을 보존한다.
- `integrations/mcp_adapter.py`: 업무와 스냅샷을 확인한 뒤 산출물 버전을 병렬 조회한다.
- `evaluation_agent/final/materials.py`: 열람·근거 연결·승인 기록, 산출물 차이,
  승인 기준 출처, 허용된 참조 문서를 각 그룹 안에서 병렬 조회한다.
  기록마다 다시 만들던 산출물 구간·버전 집합도 한 번만 만든다.
- 대화·고객 문서의 페이지 조회는 기존 순서를 유지한다. 선택적 `NOT_FOUND`와 참조 목록도
  원래 순서로 조립하여 근거 ID 및 입력의 재현성을 유지한다.

동시 실행 상한은 **수집 호출 하나당 4개**다. 여러 Worker를 띄우면 서버 전체 동시 요청 수는
늘어난다. 조회 횟수 절감이나 캐시는 도입하지 않았다. 실패 시 이미 서버가 받은 읽기 요청의
서버 측 중단까지 보장하는 것은 아니며, Agent 측 잔여 작업 종료를 보장한다.

## 비교 측정

40개 고정 사례에 대해 MCP 호출마다 `asyncio.sleep(0.020)`으로 20ms를 넣고,
사례당 3회 실행한 중앙값을 비교했다. 변경 전 코드가 로드된 프로세스에서 baseline을
측정한 뒤 개선 코드를 측정했다. 실제 서버·DB·LLM 호출은 없다.

| 지표 | 변경 전 | 변경 후 |
| --- | ---: | ---: |
| 40개 사례별 중앙값의 합 | 11,136.270ms | 7,717.323ms |
| 사례별 소요 시간의 중앙값 | 267.616ms | 195.033ms |
| 40개 사례 1회 수집의 호출 수 | 504 | 504 |
| 사례에서 관측한 최대 동시 읽기 | 1 | 3 |

사례별 중앙값의 합 기준 **30.70% 감소**했다. 샘플의 독립 요청 수 때문에 최대 3개가
관측되었고, 별도 부하·SDK 테스트에서는 상한 4개를 검증했다.

| 업무 유형 | 변경 전 중앙값 | 변경 후 중앙값 |
| --- | ---: | ---: |
| 고객 질의 답변 | 256.68ms | 178.32ms |
| 제안서 | 288.01ms | 184.90ms |
| 견적서 | 310.01ms | 203.62ms |
| RFP 분석 | 265.90ms | 194.74ms |

40개 모두 근거를 포함한 수집 결과 해시 및 도구별 호출 수가 일치했다.
별도 회귀 테스트에서 직렬·병렬 실행의 전체 JSON 문자열과 도구 인자별 호출 횟수도 비교한다.
**서비스 전체 응답 시간, 운영 처리량, 모델 정확도가 30.7% 개선됐다는 의미는 아니다.**
서버 내부에서 요청을 직렬 처리하거나 LLM 지연이 대부분이면 실제 효과는 작아질 수 있다.

## 검증과 재현

변경 전 전체 테스트는 947개 통과, 4개 건너뜀이고, 변경 후는 **995개 통과, 4개 건너뜀**이다.
변경한 Python 파일의 Ruff 검사와 `git diff --check`도 통과했다.
중간 피드백 20건·최종 평가 8건·팀 평가 8건의 품질 평가셋 입력 검사도 네트워크 호출 없이 통과했다.
추가한 테스트는 동시 실행 상한,
결과 순서, 오류·취소 정리, 선택적 조회 오류 처리, 40개 사례 동일성,
실제 MCP SDK + 로컬 ASGI 전송에서 인증 유지와 동시 요청 처리를 다룬다.
PostgreSQL이 필요한 테스트는 이 환경에서 실행되지 않는다.

```bash
.venv/bin/python -m pytest -q
.venv/bin/python tests/benchmark_evaluation_collection.py \
  --output outputs/performance/new-measurement.json
```

벤치마크는 개발용 테스트 fixture를 사용하며 기존 출력 파일을 덮어쓰지 않는다.
이번 로컬 원본 결과는 `outputs/performance/baseline.json`과
`outputs/performance/optimized.json`에 있다. `outputs/`는 Git 제외 대상이다.
소요 시간은 머신 상태에 따라 달라지므로 40건의 결과 해시·호출 횟수 동일성도 함께 확인한다.

백엔드 복구 후에는 동일 스냅샷으로 수집 구간 및 전체 평가의 p50/p95,
MCP 오류·429 비율과 서버 동시 처리 수를 비교해야 한다.
평가 품질 개선은 기존 `samples/*/quality-v1.json`과 `docs/offline_llm_quality.md`의
실제 모델 반복 실행·사람 검토 절차로 별도 측정한다. 이번에는 실제 모델 서버·DB 연결 없이
검증했으므로 생성 품질·비용 및 PostgreSQL·RabbitMQ 통합 동작은 확인하지 않았다.
