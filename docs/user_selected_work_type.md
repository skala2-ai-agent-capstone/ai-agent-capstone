# 사용자 선택 업무 유형으로 전환 — 2026-10-23

업무 시작 시 사용자가 유형 하나를 선택하고 백엔드가 저장한다.
Agent는 MCP에서 이 값을 받아 기준과 평가 흐름을 연결하며, 대화로 유형을 추측하지 않는다.
이번 변경은 Agent 측 연결부에 적용했다. 화면·업무 생성 API는 각 담당자의 구현이 필요하다.

```text
업무 시작: 사용자 유형 선택 → 백엔드가 work_type 저장
                                    ↓
중간 요청: 최근 완료 5쌍 + 저장된 유형 + 고정 기준 → 피드백
최종 요청: 업무 기록 + 저장된 유형 → 해당 유형 기준 준비·승인 → 평가
```

## 유형 코드

| 화면 표시 | DB·MCP 코드 | 기존 기준/최종 평가 내부 코드 |
|---|---|---|
| RFP 분석 | `rfp_analysis` | `rfp_analysis` |
| 제안서 작성 | `proposal` | `proposal` |
| 견적서 작성 | `quote` | `quotation` |
| 고객 질의 답변 | `inquiry_reply` | `customer_response` |

기준 담당자 코드의 이름을 일괄 변경하지 않고 Agent 연결부에서 변환한다.
현재 계약은 업무 1건에 유형 1개다. 복수 업무라면 업무를 나눠 등록한다.

## Agent 코드에 반영한 내용

- `ai_agents.cli.mcp run`, `ai_agents.cli.workflow`에서 분류 모델을 생성/호출하지 않는다.
- `get_work_case` 응답의 `data.work_type`을 읽는다. 요청자의 임의 CLI 인자로 덮어쓰지 않는다.
- 유형이 없거나 지원하지 않으면 `work_type_hold / USER_WORK_TYPE_REQUIRED`로 종료한다.
  내규 조회·기준 생성·평가로 진행하거나 LLM 분류로 자동 대체하지 않는다.
- 기준 생성기에 전달하는 유형과 평가 인계 유형이 저장된 사용자 선택과 일치하는지 확인한다.
- 승인 대상에 사용자 선택 유형을 표시하고 업무 스냅샷 hash와 함께 고정한다.
- 중간 피드백은 원래 자동 분류를 호출하지 않았다. MCP의 문맥에 저장 유형을 전달하면 된다.

기존 인계 필드명 `classification`은 호환성을 위해 유지했다. 사용자 선택의 내용은 다음과
같으며, LLM의 분류 이유·근거·모델 실행 기록을 만들어 넣지 않는다.

```json
{
  "status": "selected",
  "source": "user",
  "registered_work_type": "quote",
  "work_type": "quotation"
}
```

기존 LLM 분류 결과는 `status=classified`로 별도 구분된다. 과거 실험과 회귀 테스트를 위해
`classification/`, 독립 분류 CLI 및 classifier를 명시적으로 주입하는 그래프 API는 남겼다.
일반 실행은 `build_agent_graph(gateway, None, builder)`를 사용하며,
그래프에는 `classify_work` 대신 `select_work_type` 노드가 들어간다.
평가 기준 생성 프롬프트·채점·코칭 로직은 변경하지 않았다.

## 담당자별 반영 사항

**프론트:** 업무 생성 화면에서 위 유형 하나를 필수 선택하고 서버에 코드로 보낸다.
표시 이름을 데이터 코드로 저장하거나 자동 분류 대기 화면을 띄우지 않는다.

**백엔드:** 업무 생성 시 유형 enum과 본인 권한을 검사해 `work_type`을 저장한다.
평가 요청 시점의 유형·기준 버전을 함께 고정한다. 업무 유형 수정이 허용된다면 이전 평가의
유형과 기준을 소급 변경하지 않고, 이후 요청부터 새 유형/기준으로 평가한다.
수정 허용 시점·권한은 별도 제품 정책으로 정해야 한다.

**MCP:** `get_work_case.work_type`과 `start_live_evaluation.data.work_type`에 저장된 유형을
반환한다. 중간 피드백은 `quote/inquiry_reply` 등 DB·MCP 코드를 사용한다.
새 업무에서 유형이 빠지면 백엔드가 요청을 거부한다. 중간 피드백의 nullable 유형 계약은
기존 가상 평가셋/이전 요청 호환용으로 남아 있으며, Agent가 누락 유형을 자동 분류하지 않는다.

**기준 담당:** 업무 유형을 새로 분류할 필요 없이, 전달받은 유형에 대한 기준 로직을 유지한다.
기준 생성 시점·승인·버전 관리는 별도의 흐름이며 이번 변경으로 자동 변경하지 않는다.
